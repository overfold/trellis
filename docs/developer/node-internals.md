# Runtime, networking, storage, and secrets

## Agent convergence

The server submits one allocation containing all tasks in a group. The agent validates epoch/generation, serializes local reconciliation, prepares network/volumes/secrets/ports, and asks the selected runtime to create/start containers. Runtime labels retain allocation identity and generation so an agent can verify ownership after restart, while the durable agent record remains authoritative for control epoch and drain intent. Recovery refuses to start the node when fencing state or allocation records are unreadable, malformed, or missing for an existing managed container. A genuinely empty first boot is accepted without a pre-existing control epoch. Delete operations are likewise generation-aware. Before a rolling replacement or node evacuation, an explicit drain operation suppresses local automatic restarts until the normal stop arrives. Drain state and its sequence belong to the allocation generation: task records keep them through agent recovery, and every start request carries the control plane's current drain state (outside the execution hash). The agent keeps whichever of that state and its locally applied drain or resume has the higher sequence (the request on a tie) and applies the result to tasks already running before starting any task, so a retried start, or a task the agent had no record of when the drain arrived, starts restart-suppressed and rejects older drain or resume sequences. Heartbeats report observations only; desired-vs-observed cleanup belongs to the server reconciler. The agent API is an internal control surface, not a user API.

Failed starts retain a stopping allocation record when cleanup fails, so a subsequent start, stop, or agent recovery can finish cleanup. Port claims remain reserved until cleanup and record deletion succeed. When container creation has an ambiguous result, cleanup first verifies the container's execution labels or confirms that its ID is absent; absence from the cluster-filtered container listing alone is not enough. Unverified ownership preserves the allocation and its resources rather than risking cleanup of another execution. When recovery, including a recovery retry after a failed or incomplete listing, observes the recorded container and its runtime labels match the record's cluster, allocation ID, generation, job revision, execution hash, namespace, job, group, and task, the agent clears the unverified flag and saves the record, so the task becomes an exec and metrics target again. A container whose state stays unreadable, or whose labels differ, keeps the flag; a mismatch is retained as stopping.

Agent recovery never treats an unreadable container as absent. The runtime listing reports a recorded container whose metadata or task state cannot be read with unknown status. Its allocation is kept in memory with its last recorded phase and adopted port claims, local restarts are suppressed, and heartbeats report it with unknown health until it is observed; its durable record is left unchanged. Only a successful listing that omits a recorded container confirms it is missing. The agent retries with backoff until each such allocation is observed, then applies normal recovery. Because the control plane rejects stops for a superseded generation, the agent retries stopping any retained stopping record with verified ownership and a newer known generation until the stop succeeds, including after a restart. A start retry inspects an unobserved allocation's container itself and is refused while its state stays unreadable. A stop issued meanwhile goes to the runtime and returns its error rather than reporting success.

The listing reports a container whose task was deleted as stopped, and a paused task as paused rather than unknown. A paused container exists, so recovery classifies it at once instead of retrying: it keeps its allocation and port claims and is never restarted or replaced. Trellis never pauses containers itself. Because the frozen processes cannot serve, a paused allocation reports lifecycle `running` with health `unhealthy`. Configured health checks keep probing it and report `healthy` once it is resumed; without a health check it stays `unhealthy` until the agent observes it running again, through agent recovery or a local restart. Exec refuses a paused container because it is not running. A runtime stop resumes a paused task before signalling it, so the task gets the normal graceful `SIGTERM` stop.

## Runtime abstraction

`ContainerRuntime` provides create/start/stop/remove/status/list/log and exec operations. `ManagedRuntime` adds lifecycle management. The containerd implementation creates OCI containers, applies task environment/resources/mounts/ports/runtime selection, and streams logs. Resources map to a CFS CPU quota, a memory limit with an equal memory+swap limit (omitted on cgroup v1 without memsw accounting, and for `runsc` on cgroup v2 when no top-level cgroup exposes `memory.swap.max`; runc itself skips a missing `memory.swap.max`), and a pids limit. The agent supplies the pids limit from node configuration on every create; it is node policy outside the canonical spec and execution hash, so changing it never restarts or fences existing allocations. Exec processes inherit the container's OCI environment, user, and working directory so one-shot commands, script health checks, and interactive terminals share the task process context. `runc` is normal OCI execution; `runsc` requires a matching containerd runtime installation. `InjectedRuntime` and its fault file exist for deterministic tests and must not host real workloads.

Exec, interactive exec sessions, and allocation metrics address only task records that are running, have verified container ownership, and belong to the newest generation the agent holds for the allocation that is not stopping; starting, stopping, unverified, and other-generation records are never targets, and exec also confirms that the target container is running. Metrics are empty while no current-generation task runs. Without a task name, the agent selects the single running task and rejects the request when several run. A one-shot exec process is killed and deleted when its request is cancelled. Each interactive session is bound to one task record and container: stopping that record closes only its sessions, before the runtime stop is attempted, and a session whose target stops while it is being created is closed instead of registered. The agent releases an exited session's output buffer shortly after exit, closes sessions idle for 30 minutes, and on graceful shutdown closes all sessions and refuses new ones. Sessions are not persisted, so exec processes left behind by an agent crash keep running in their containers until they exit or the container stops.

## Ports and health

A host port of zero requests allocation by the node port manager; a nonzero port reserves that exact host port. Reported mappings feed status and service discovery. Health checks run on configured intervals/timeouts and require a threshold of failures/successes before state changes. Script probes execute the supplied command in the task context. HTTP and TCP checks execute the dedicated helper mounted read-only at `/run/trellis/health-probe`, so they probe task-local loopback in host, isolated, and namespace networking with either supported runtime.

## Volumes

A volume is identified for scheduling by `(namespace, name)`. The control plane loads an authoritative Raft-backed registry before scheduling. When an identity is unseen, the scheduler reserves it to the node selected for first placement and persists that binding **before** starting the new allocation. Later allocations using the same identity may run only on that node, including after leader restart or while the owner is offline. The node also persists `namespace/name -> host path` locally and reports its known registrations for diagnostics, but heartbeat advertisements do not create or override control-plane ownership.

`host_path` controls only the node-side backing path. `@/relative/path` resolves below `<data-dir>/volumes/namespaces/<namespace>/` and the volume manager creates the directory. A clean absolute path is used verbatim and must already exist. Absolute paths deliberately bypass filesystem-level namespace separation, although the logical registration remains namespace-scoped. `container_path` is the absolute destination passed to the runtime; `read_only` changes the OCI mount.

The agent resolves an `@/` path component by component without following symlinks, then bind-mounts the resolved directory at a Trellis-owned staging path below `<data-dir>/volume-staging/`. That staging path, not the tenant-writable volume path, becomes the OCI mount source, so containerd never re-resolves a path a workload could have replaced. containerd resolves mount sources again whenever it creates a task, including in-place restarts, so the staging mount lives as long as the container: it is released only after the container is removed or a failed start is cleaned up. On restart, the agent keeps staging mounts for containers that still exist and removes the rest. Staging mounts are created in the agent's mount namespace, so the agent must run in the host mount namespace. Running it in a private mount namespace is unsupported: for example, under a systemd unit with `PrivateMounts=`, `PrivateTmp=`, `ProtectSystem=`, `ProtectHome=`, `ReadOnlyPaths=`, or `InaccessiblePaths=`, inside a container without shared mount propagation, or under `unshare -m`. There the staging mounts are invisible to containerd, and they disappear when the agent exits, so tasks recreated later, including in-place restarts, cannot resolve their volume mount source. A start refuses staging still held by an existing container with the same ID, and releases staging left behind for a container that no longer exists.

Volume registrations and their data outlive individual allocations. Changing `host_path` for an existing name changes its backing path on the already owning node; Trellis does not move bytes. Volume registration is locality metadata, not replication, snapshots, migration, or distributed storage. Desired-state backups preserve the registry metadata, but never the volume bytes.

## Networking

Host mode bypasses allocation isolation. Namespace-networked allocations receive an automatically derived namespace address and WireGuard peer plan. Each namespace has a separate bridge, subnet, WireGuard interface, and peer set on a node, so namespace traffic follows a structurally separate network path rather than sharing one WireGuard device. The control plane durably assigns each namespace with desired or active namespace-networked allocations a slot in the configured WireGuard UDP port range; every node uses that slot as an offset from its local and advertised base ports. The slot remains stable across allocation replacement and leader changes while the namespace still needs a network path, then is released after the last namespace-networked allocation is gone. On each node, later allocations in the same namespace reuse the existing bridge/WireGuard pathway; detaching the last local allocation removes that node's namespace interface, bridge, firewall rules, and lease directory. Before attaching, the agent durably records the attachment intent (allocation ID, namespace, and network) on the allocation record, and the node network manager journals each attachment below its state directory before creating the network namespace, veth pair, or address lease. Cleanup of a failed start, a stop, or recovery of a missing container detaches by allocation ID when the record holds only the intent, so a crash during attach cannot strand `/var/run/netns/<allocation>`, its veths, or its lease; detaching skips resources that are already gone and keeps the journal entry until every one of them is removed. At startup, under the same gates as the secret sweep (durable storage, every allocation record readable, and recovery having listed every container, including a listing that completes late), the agent detaches journaled attachments that no allocation record or in-memory allocation owns. The manager only acts on attachments it journaled and on names derived from them, so it never touches network state Trellis did not create. The leader deterministically derives namespace subnets and node peer information from the configured cluster pool. The node manager materializes interfaces/routes/peers; disabled networking returns an explicit capability error.

Every container receives the same Trellis workload resolver in `resolv.conf`. The resolver listens on the reserved node-local address `198.18.0.53:53` over UDP and TCP and forwards ordinary names to the node's upstream resolvers. Internal `*.trellis` discovery is available to namespace-networked workloads: the resolver derives the caller namespace from the source address and the network manager's durable attachment records, then answers only a matching `group.job.namespace.trellis` name. Unknown sources and cross-namespace names receive no discovery records. The node fetches catalog entries over its authenticated control-plane connection only for namespaces with active allocations assigned to it.

Forwarding isolation uses the Trellis-owned `TRELLIS-FORWARD` chain, reached by a jump reconciled at position 1 of the shared `FORWARD` chain. Per-bridge source-spoofing and cross-interface DROP rules live in that owned chain, so a host rule that accepts traffic later in `FORWARD` cannot bypass them. Reconciliation creates the chain idempotently, restores the first-position jump after restart or external rule changes, and removes legacy direct rules. Detaching the final local namespace path removes its rules, the shared jump, and the empty owned chain; the attachment journal is retained if cleanup fails so recovery retries the same teardown. Namespace INPUT rules permit DNS to the internal resolver only from the namespace's node-local subnet. Namespace-networked container OCI specs also omit `CAP_NET_RAW` by default as defense in depth.

## Secrets and API access

The secret store accepts at most 64 KiB, encrypts values with the configured 32-byte key, stores versioned ciphertext and key ID in durable replicated state, and exposes metadata without plaintext. The API, dashboard proxy, and CLI bound inputs before decoding or fully reading an oversized value. Secret delivery occurs during allocation start. Both environment and file targets are materialized below a randomly named, agent-private (`0700`) root on `/dev/shm`; the agent verifies with `statfs` that the backing filesystem is actually tmpfs before writing any plaintext. tmpfs avoids durable filesystem persistence, but Linux may move tmpfs pages to swap. Operators requiring protection from offline swap inspection must disable swap or use encrypted swap.

File targets are mounted below `/run/trellis-secrets/` with their requested owner-only mode. After containerd resolves the image-configured user, Trellis changes each secret source's numeric owner to that OCI UID/GID before task creation, so non-root images can read their files without group/world access. Environment targets and the workload API token are mounted in a private internal directory, and the Trellis task-local helper loads them immediately before `exec` of the image command. The persisted containerd OCI spec therefore contains only the helper invocation, mount paths, and ordinary non-secret environment, not managed secret plaintext or the API token. The resulting application process still necessarily contains environment-delivered values in its live process environment; same-container code and host inspection permitted by the kernel can observe them. Prefer file targets when the application supports them.

The agent durably records its secret root before first use and each task's directory before writing any plaintext, and never starts into a directory that already exists. At startup, once recovery succeeds, it removes any directory under the recorded root that no allocation record owns, so a crash during allocation start cannot strand secret files until reboot. A recorded root that is gone or not owned by the agent user is replaced; one the agent owns but that other users can access is refused rather than abandoned. Cleanup only removes directories below a root the agent still owns; a root path that another user recreated after a reboot holds none of the agent's secrets, so cleanup treats it as already gone instead of following or blocking on it.

API access is a task-group mode. With `api_access: namespace`, the control plane obtains or creates a persistent bearer token for the allocation job's own namespace. With `api_access: cluster`, it creates a scoped cluster bearer token; it never injects the administrator or enrollment credential. Both modes inject `TRELLIS_ADDR`, `TRELLIS_TOKEN`, and `TRELLIS_NAMESPACE`, where the namespace variable is always the job namespace; `TRELLIS_CA_CERT` is added when the cluster CA is available. `TRELLIS_ADDR` uses the certificate identity `trellis`; the agent maps that name to loopback for host networking or to the namespace gateway for namespace networking so callers never depend on the host OS hostname or a stale leader address.

Namespace authorization is carried in the persisted token scope, not trusted from the environment or request header, so changing `TRELLIS_NAMESPACE` cannot escape the job namespace. Cluster-scoped workload requests receive ordinary cluster read/write authority, so the default namespace is only a client convenience for that mode. Every task in the group receives the selected credential, making the task-group boundary a security boundary as well as a lifecycle boundary.
