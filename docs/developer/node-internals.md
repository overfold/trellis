# Runtime, networking, storage, and secrets

## Agent convergence

The server submits one allocation containing all tasks in a group. The agent validates epoch, generation, and execution hash, rejects a generation whose restart budget is exhausted, and then accepts the start and returns: it pulls the images and creates and starts the tasks in the background, so an image pull of any length never holds the start request open. The pull runs without the per-allocation operation lock, so stops, drains, resumes, and start retries of the allocation proceed meanwhile; the agent then takes the lock, stops older generations, prepares network/volumes/secrets/ports, and asks the selected runtime to create/start containers. Heartbeats report the tasks of an accepted start that have no record yet as `starting`. A retried start for the same generation and execution while the start runs, or once it runs, is accepted without starting again. Such a retry is accepted without the operation lock, so it never waits for task creation. A stop of the generation, or a start of a newer one, cancels a start still in progress and waits for its cleanup; a stop, drain, or start for an older generation is rejected as stale while the newer start runs, but not once it has failed, so the control plane can still stop the older generation it never replaced. A drain or resume delivered during the pull is applied when the tasks are created. Before creating tasks the start checks that a leader of the current control epoch requested it (a retry from the new leader refreshes that); otherwise it ends without creating anything or reporting a failure, and the new leader's next start begins it again. A start still running after 30 minutes is cancelled and reported as failed. A failed background start is reported in heartbeats with the start request's `attempt`, and with an operation code when retrying the generation cannot fix it, until a start request with a different attempt, a stop, or a newer generation replaces it, so the control plane counts each failure once. Accepted starts are not persisted: after an agent restart during a pull nothing describes the start, and the control plane's next start request, sent while the allocation stays `starting`, begins it again; a restart during container creation leaves task records that recovery and the retried start resolve as below. Runtime labels retain allocation identity and generation so an agent can verify ownership after restart, while the durable agent record remains authoritative for control epoch and drain intent. Recovery refuses to start the node when fencing state or allocation records are unreadable, malformed, or missing for an existing managed container. A genuinely empty first boot is accepted without a pre-existing control epoch; a missing epoch is refused when records or managed containers exist, or when the runtime cannot be listed to prove that none do. A failed runtime listing is otherwise retryable, not fatal: recovery loads the recorded epoch, keeps every record as unobserved (below), and `Init` starts heartbeats, the reconciler, and the recovery retry. When a late listing succeeds, the retry applies startup's rule: a labelled container of the cluster without a record is never adopted from its labels. The agent reports the error through `Agent.Failed`, the daemon exits, and the restart refuses the same container at `Init`. Exiting is visible to operators and matches startup, whereas silently blocking recovery would keep an unmanaged container running indefinitely. A container that is gone when re-inspected under its allocation lock, or whose metadata is unreadable, is listed again instead. Refusal errors name the file or container and point to the operator steps in [Operations](../public/operations.md#agent-recovery-refused): restore containerd when it cannot list containers; remove a container that has no record with `ctr` rather than writing a record for it; and restore damaged agent state from backup, or remove the cluster's containers and move `agent/allocations` and `agent/control-epoch` aside so the node restarts empty. Delete operations are likewise generation-aware. Before a rolling replacement or node evacuation, an explicit drain operation suppresses local automatic restarts until the normal stop arrives. Drain state and its sequence belong to the allocation generation: task records keep them through agent recovery, and every start request carries the control plane's current drain state (outside the execution hash). The agent keeps whichever of that state and its locally applied drain or resume has the higher sequence (the request on a tie) and applies the result to tasks already running before starting any task, so a retried start, or a task the agent had no record of when the drain arrived, starts restart-suppressed and rejects older drain or resume sequences. Heartbeats report observations only; desired-vs-observed cleanup belongs to the server reconciler. The agent API is an internal control surface, not a user API.

Failed starts retain a stopping allocation record when cleanup fails, so a subsequent start, stop, or agent recovery can finish cleanup. Port claims remain reserved until cleanup and record deletion succeed. When container creation has an ambiguous result, cleanup first verifies the container's execution labels or confirms that its ID is absent; absence from the cluster-filtered container listing alone is not enough. Unverified ownership preserves the allocation and its resources rather than risking cleanup of another execution. Recovery proves ownership for every recorded container, regardless of its durable verification flag: its runtime labels must match the record's cluster, allocation ID, generation, job revision, execution hash, namespace, job, group, and task before the agent health-checks, execs, restarts, stops, or removes it. A match clears any unverified flag and is saved; a container whose state stays unreadable, or whose labels differ, is marked unverified and retained as stopping with all of its resources.

Agent recovery never treats an unreadable container as absent. The runtime listing reports a recorded container whose metadata or task state cannot be read with unknown status. Its allocation is kept in memory with its last recorded phase and adopted port claims, local restarts are suppressed, and heartbeats report it with unknown health until it is observed; its durable record is left unchanged. Only a successful listing that omits a recorded container confirms it is missing. The agent retries with backoff until each such allocation is observed, then applies normal recovery. The same applies to every record after a failed initial listing; the orphaned secret and network sweep waits until a listing completes. Because the control plane rejects stops for a superseded generation, the agent retries stopping any retained stopping record with verified ownership and a newer known generation until the stop succeeds, including after a restart. A start retry inspects an unobserved allocation's container itself and is refused while its state stays unreadable. A stop issued meanwhile goes to the runtime and returns its error rather than reporting success.

Local restart accounting is persisted before the runtime restart begins. If that write fails, the agent leaves the stopped container and its budget unchanged and retries reconciliation later; therefore a crash cannot repeat a restart against an older durable counter. Explicit stop and drain operations retain their existing restart-suppression behavior and do not wait for restart-account persistence to recover.

The listing reports a container whose task was deleted as stopped, and a paused task as paused rather than unknown. A paused container exists, so recovery classifies it at once instead of retrying: it keeps its allocation and port claims and is never restarted or replaced. Trellis never pauses containers itself. Because the frozen processes cannot serve, a paused allocation reports lifecycle `running` with health `unhealthy`. Configured health checks keep probing it and report `healthy` once it is resumed; without a health check it stays `unhealthy` until the agent observes it running again, through agent recovery or a local restart. Exec refuses a paused container because it is not running. A runtime stop resumes a paused task before signalling it, so the task gets the normal graceful `SIGTERM` stop.

## Runtime abstraction

`ContainerRuntime` provides create/start/stop/remove/status/list/log and exec operations. `ManagedRuntime` adds lifecycle management. The containerd implementation creates OCI containers, applies task environment/resources/mounts/ports/runtime selection, and streams logs. Resources map to a CFS CPU quota, a memory limit with an equal memory+swap limit (omitted on cgroup v1 without memsw accounting, and for `runsc` on cgroup v2 when no top-level cgroup exposes `memory.swap.max`; runc itself skips a missing `memory.swap.max`), and a pids limit. The agent supplies the pids limit from node configuration on every create; it is node policy outside the canonical spec and execution hash, so changing it never restarts or fences existing allocations. Exec processes copy the container's whole OCI process (user and supplementary groups, environment, working directory, capabilities, rlimits, `no_new_privs`, and AppArmor/SELinux labels) and replace only the arguments and terminal settings (an empty working directory becomes `/`, and a task with environment secrets runs the command through the probe's `env-exec` wrapper), so exec streams, with or without a terminal, and health checks share the task process context and security confinement; the seccomp filter is container-wide. When the container spec or its process cannot be read, exec fails instead of falling back to a default process. `runc` is normal OCI execution; `runsc` requires a matching containerd runtime installation. `InjectedRuntime` and its fault file exist for deterministic tests and must not host real workloads: `trellis` accepts `--runtime injected` and `--runtime-faults` only when built with `-tags=integration`, and an injected node advertises no optional capabilities such as `runtime.runsc` or `network.namespace`.

containerd's client default spec applies no seccomp filter or AppArmor profile, so the containerd implementation hardens every workload spec itself:

- `CAP_MKNOD` and `CAP_NET_RAW` are removed from containerd's default capability set in every networking mode and runtime.
- containerd's default seccomp profile is applied after the capability change, since the profile derives its allowed syscalls from the final capability set. It is included for `runsc` as well: gVisor ignores OCI seccomp unless started with `--oci-seccomp`, in which case it enforces the profile inside the sandbox.
- When the host supports AppArmor (enabled in the kernel and `/sbin/apparmor_parser` present), non-`runsc` workloads run under the `trellis-default` profile, generated from containerd's default template and loaded on first use. Starting a task reloads the profile if it has since been unloaded, so in-place restarts keep working. Creating a container or starting its task fails if the profile cannot be loaded; exec fails rather than running without the container's security context when the container spec cannot be read. `runsc` ignores OCI AppArmor profiles, so none is set for it.
- Every Trellis-generated bind mount (volumes, secret files, `/etc/resolv.conf`, `/etc/hosts`, and the health probe) carries `nosuid` and `nodev`, so setuid binaries and device nodes in a mount source have no effect inside the container. `noexec` is not added; volumes and the health probe stay executable. The flags apply to the mount itself, not to mounts nested below an absolute host path.

Exec streams and allocation metrics address only task records that are running, have verified container ownership, and belong to the newest generation the agent holds for the allocation that is not stopping; starting, stopping, unverified, and other-generation records are never targets, and exec also confirms that the target container is running. Metrics are empty while no current-generation task runs. Without a task name, the agent selects the single running task and rejects the request when several run. An exec stream accepts the leader's control epoch before it is admitted, so a stream from a deposed leader is rejected, and ends when the agent later accepts a newer epoch. Each stream is bound to one task record and container: stopping that record ends only its streams and kills their processes before the runtime stop is attempted, and a process whose target stops while it is being started is killed instead of registered. A stream's process is killed when its connection closes, when it is idle for 30 minutes, after eight hours, or when the agent shuts down gracefully, and new streams are refused during shutdown. A stream's admission slot is held until its process has exited; a process that survives a kill keeps its slot while the kill is retried. Process output is copied to the stream as it is produced, with no agent-side buffer, and at most four input frames are queued ahead of the process. Streams are not persisted, so exec processes left behind by an agent crash keep running in their containers until they exit or the container stops.

## Ports and health

A host port of zero requests allocation by the node port manager; a nonzero port reserves that exact host port. Reported mappings feed status and service discovery. Health checks run on configured intervals/timeouts and require a threshold of failures/successes before state changes. Script probes execute the supplied command in the task context. HTTP and TCP checks execute the dedicated helper mounted read-only at `/run/trellis/health-probe`, so they probe task-local loopback in host, isolated, and namespace networking with either supported runtime. The helper shares the control plane's path validation (`internal/probepath`), builds the HTTP URL from a fixed loopback host and the validated origin-form path, bypasses proxies, never resolves names (`localhost` maps directly to `127.0.0.1`), dials only `127.0.0.1`, and follows redirects only while they stay on that address and the probed port. The probe's usage exit status (`probepath.UsageExit`, 64) is returned as a health-check error, so the agent logs it with the container ID; the check still counts as failed.

## Volumes

A volume is identified for scheduling by `(namespace, name)`. The control plane loads an authoritative Raft-backed registry before scheduling. When an identity is unseen, the scheduler reserves it to the node selected for first placement and persists that binding **before** starting the new allocation. Later allocations using the same identity may run only on that node, including after leader restart or while the owner is offline. The node also persists `namespace/name -> host path` locally and reports its known registrations for diagnostics, but heartbeat advertisements do not create or override control-plane ownership.

`host_path` controls only the node-side backing path. `@/relative/path` resolves below `<data-dir>/volumes/namespaces/<namespace>/` and the volume manager creates the directory. A clean absolute path is used verbatim and must already exist. Absolute paths deliberately bypass filesystem-level namespace separation, although the logical registration remains namespace-scoped. `container_path` is the absolute destination passed to the runtime; `read_only` changes the OCI mount.

The agent resolves an `@/` path component by component without following symlinks, then bind-mounts the resolved directory at a Trellis-owned staging path below `<data-dir>/volume-staging/`. That staging path, not the tenant-writable volume path, becomes the OCI mount source, so containerd never re-resolves a path a workload could have replaced. containerd resolves mount sources again whenever it creates a task, including in-place restarts, so the staging mount lives as long as the container: it is released only after the container is removed or a failed start is cleaned up. On restart, the agent keeps staging mounts for containers that still exist and removes the rest. Staging mounts are created in the agent's mount namespace, so the agent must run in the host mount namespace. Running it in a private mount namespace is unsupported: for example, under a systemd unit with `PrivateMounts=`, `PrivateTmp=`, `ProtectSystem=`, `ProtectHome=`, `ReadOnlyPaths=`, or `InaccessiblePaths=`, inside a container without shared mount propagation, or under `unshare -m`. There the staging mounts are invisible to containerd, and they disappear when the agent exits, so tasks recreated later, including in-place restarts, cannot resolve their volume mount source. A start refuses staging still held by an existing container with the same ID, and releases staging left behind for a container that no longer exists.

Volume registrations and their data outlive individual allocations. Changing `host_path` for an existing name changes its backing path on the already owning node; Trellis does not move bytes. Volume registration is locality metadata, not replication, snapshots, migration, or distributed storage. Desired-state backups preserve the registry metadata, but never the volume bytes.

## Networking

Host mode bypasses allocation isolation. Namespace-networked allocations receive an automatically assigned namespace address and WireGuard peer plan. Each namespace has a separate bridge, subnet, WireGuard interface, and peer set on a node, so namespace traffic follows a structurally separate network path rather than sharing one WireGuard device. The control plane durably assigns each namespace with desired or active namespace-networked allocations a slot in the configured WireGuard UDP port range; every node uses that slot as an offset from its local and advertised base ports. The slot remains stable across allocation replacement and leader changes while the namespace still needs a network path, then is released after the last namespace-networked allocation is gone. On each node, later allocations in the same namespace reuse the existing bridge/WireGuard pathway; detaching the last local allocation removes that node's namespace interface, bridge, firewall rules, and lease directory. Before attaching, the agent durably records the attachment intent (allocation ID, namespace, and network) on the allocation record, and the node network manager journals each attachment below its state directory before creating the network namespace, veth pair, or address lease. Cleanup of a failed start, a stop, or recovery of a missing container detaches by allocation ID when the record holds only the intent, so a crash during attach cannot strand `/var/run/netns/<allocation>`, its veths, or its lease; detaching skips resources that are already gone and keeps the journal entry until every one of them is removed. At startup, under the same gates as the secret sweep (durable storage, every allocation record readable, and recovery having listed every container, including a listing that completes late), the agent detaches journaled attachments that no allocation record or in-memory allocation owns. The manager only acts on attachments it journaled and on names derived from them, so it never touches network state Trellis did not create. The control plane also durably assigns each (namespace, node) pair a subnet index for every namespace that needs a network path and every registered node. The leader plans these registrations before building network plans and commits them with the reconciliation pass: existing registrations are kept, new pairs take the lowest free index in namespace then node ID order, and registrations are released when the namespace no longer has desired or active namespace-networked allocations or the node is no longer registered. Index *i* selects the *i*-th `/24` of the cluster `wireguard_pool` as the node's namespace subnet and `169.254.1.0` + *i* as its WireGuard link address, so no two registrations share a subnet or link address. A pool therefore addresses at most `min(2^(24 - prefix length), 65024)` namespace-node pairs; the default `/10` holds 16384. A namespace receives new registrations only when it can be addressed on every node. When the pool cannot hold it, the leader logs the exhaustion, keeps existing registrations, and withholds new placements for that namespace instead of reusing an address. A node added to an exhausted pool is not a peer for namespaces it could not be addressed in. Subnet registrations are desired state and are included in backups; restoring into a cluster whose nodes have different IDs releases them on the first reconciliation. The node manager materializes interfaces/routes/peers; disabled networking returns an explicit capability error.

Every container receives the same Trellis workload resolver in `resolv.conf`. The resolver listens on the reserved node-local address `198.18.0.53:53` over UDP and TCP and forwards ordinary names to the node's upstream resolvers. Internal `*.trellis` discovery is available to namespace-networked workloads: the resolver derives the caller namespace from the source address and the network manager's durable attachment records, then answers only a matching `group.job.namespace.trellis` name. Unknown sources and cross-namespace names receive no discovery records. The node fetches catalog entries over its authenticated control-plane connection only for namespaces with active allocations assigned to it.

Forwarding and host-bound isolation use the Trellis-owned `TRELLIS-FORWARD` and `TRELLIS-INPUT` chains, reached by jumps reconciled at position 1 of the shared `FORWARD` and `INPUT` chains. Per-bridge source-spoofing and cross-interface DROP rules live in `TRELLIS-FORWARD`; per-bridge ACCEPT rules for DNS to the internal resolver and, when API access is enabled, the node API on the gateway, followed by a per-bridge DROP for all other host-bound traffic, live in `TRELLIS-INPUT`. Because Trellis evaluates first, a host rule that accepts traffic in `FORWARD` or `INPUT` (for example from ufw or firewalld) cannot bypass them. Accepts are inserted at the head of `TRELLIS-INPUT` and DROPs appended, so each bridge's accepts precede its DROP. Accepts match only the namespace's node-local subnet as source. Reconciliation creates the chains idempotently and restores the first-position jumps after restart or external rule changes. Detaching the final local namespace path removes its rules, the shared jumps, and the flushed owned chains; the attachment journal is retained if cleanup fails so recovery retries the same teardown. Container OCI specs omit `CAP_NET_RAW` in every networking mode, including host mode, where raw and packet sockets could otherwise sniff and inject on every namespace bridge and WireGuard interface.

## Secrets and API access

The secret store accepts at most 64 KiB, encrypts values with the configured 32-byte key, stores versioned ciphertext and key ID in durable replicated state, and exposes metadata without plaintext. The API and CLI bound inputs before decoding or fully reading an oversized value. Secret delivery occurs during allocation start. Both environment and file targets are materialized below a randomly named, agent-private (`0700`) root on `/dev/shm`; the agent verifies with `statfs` that the backing filesystem is actually tmpfs before writing any plaintext. tmpfs avoids durable filesystem persistence, but Linux may move tmpfs pages to swap. Operators requiring protection from offline swap inspection must disable swap or use encrypted swap.

File targets are mounted below `/run/trellis-secrets/` with their requested owner-only mode. After containerd resolves the image-configured user, Trellis changes each secret source's numeric owner to that OCI UID/GID before task creation, so non-root images can read their files without group/world access. Environment targets and the workload API token are mounted in a private internal directory, and the Trellis task-local helper loads them immediately before `exec` of the image command. The persisted containerd OCI spec therefore contains only the helper invocation, mount paths, and ordinary non-secret environment, not managed secret plaintext or the API token. The resulting application process still necessarily contains environment-delivered values in its live process environment; same-container code and host inspection permitted by the kernel can observe them. Prefer file targets when the application supports them.

The agent durably records its secret root before first use and each task's directory before writing any plaintext, and never starts into a directory that already exists. At startup, once recovery succeeds, it removes any directory under the recorded root that no allocation record owns, so a crash during allocation start cannot strand secret files until reboot. A recorded root that is gone or not owned by the agent user is replaced; one the agent owns but that other users can access is refused rather than abandoned. Cleanup only removes directories below a root the agent still owns; a root path that another user recreated after a reboot holds none of the agent's secrets, so cleanup treats it as already gone instead of following or blocking on it.

API access is a task-group mode with independent `scope` (`namespace` or `cluster`) and `access` (`read` or `write`) fields. The control plane obtains or creates one bearer token per allocation generation, bound to the job and task group as its subject and restricted to the job's own namespace under namespace scope; replicated state holds only its hash and a copy sealed with the secrets key, so start retries re-deliver the same token (see [API access](api.md)). It never injects the administrator or enrollment credential. Both scopes inject `TRELLIS_ADDR`, `TRELLIS_TOKEN`, and `TRELLIS_NAMESPACE`, where the namespace variable is always the job namespace; `TRELLIS_CA_CERT` is added when the cluster CA is available. `TRELLIS_ADDR` uses the certificate identity `trellis`; the agent maps that name to loopback for host networking or to the namespace gateway for namespace networking so callers never depend on the host OS hostname or a stale leader address.

Namespace authorization is carried in the persisted token scope, not trusted from the environment or request header, so changing `TRELLIS_NAMESPACE` cannot escape the job namespace. Cluster-scoped workload requests receive ordinary cluster read/write authority, so the default namespace is only a client convenience for that mode. Every task in the group receives the selected credential, making the task-group boundary a security boundary as well as a lifecycle boundary.
